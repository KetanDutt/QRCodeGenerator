# Privacy & Security

The tool processes personal data (names, phone numbers, e-mail addresses, optionally blood groups and emergency contacts). This document describes how that data is handled and what operators should know.

## Data handling summary

| Question | Answer |
| --- | --- |
| Is the CSV uploaded anywhere? | **No.** It is read with the browser's File API and stays in page memory. |
| Are QR codes generated by an external service? | **No.** Version 1 sent every vCard to `api.qrserver.com`; since version 2 codes are rendered locally by a vendored library. |
| Does the page make any network requests? | None after it has loaded. Fonts are system fonts, icons are inline, libraries are local. It works offline. |
| What is stored persistently? | Only UI preferences in `localStorage` (`qrgen.theme`, `qrgen.settings`): theme, image size, error-correction level, download format, the default company name and the include-field toggles. **No contact data.** |
| What happens when the tab is closed or "Clear" is pressed? | All contact data and generated images are discarded. |
| Is anything logged? | No analytics, no telemetry, no cookies. |

## What ends up inside a QR code

Exactly the fields documented in [VCARD_OUTPUT.md](VCARD_OUTPUT.md): name, organisation, designation, work phone, e-mail, and - if present in the CSV and enabled in Settings - the emergency contact number, employee ID and blood group.

Think about the audience before printing: anyone who scans the badge obtains this information. The **Include in the vCard** settings let you leave out the emergency contact, employee ID or blood group without changing the CSV. The preview dialog shows the exact text that will be encoded.

## Recommendations for operators

1. **Run it locally or on an intranet.** Because no server component exists, the safest deployment is a local folder or an internal static host; see [DEPLOYMENT.md](DEPLOYMENT.md).
2. **Keep source CSVs out of version control and shared drives.** The repository's `.gitignore` excludes `*.csv` outside `samples/` to prevent accidental commits of real employee data.
3. **Use sample data for demos and bug reports.** `samples/` contains fictitious records only.
4. **Treat the ZIP output as personal data.** It contains `.vcf` files and a `manifest.csv` with the same details as the codes.
5. **Delete downloads you no longer need.** The tool cannot manage files once they are on disk.
6. **Prefer error-correction level M or Q** for badges; level H makes codes denser and harder to scan when printed small, without a privacy benefit.

## Threat model

| Threat | Mitigation |
| --- | --- |
| Data exfiltration to third parties | No runtime network access; strict CSP recommended (`connect-src 'self'`, `default-src 'none'`). |
| Malicious CSV content (script injection) | All values are inserted with `textContent`; no HTML is built from data. The CSV parser is a state machine with no `eval`/regex-DoS patterns. |
| Malicious file names in the ZIP | Names are sanitised to letters, digits, `.`, `_`, `-`; path separators and Windows-reserved names are removed; duplicates are suffixed. |
| Supply-chain risk in dependencies | Two runtime libraries, vendored and pinned (`vendor/`), no CDN; `npm install` is only needed for optional test tooling. |
| Clickjacking / framing | Send `frame-ancestors 'none'` in production (see deployment guide). |
| Local storage leakage | Only preferences are stored; nothing sensitive. |

## Vulnerability reports

Please report security issues privately to the author (contact details in [LICENSE](../LICENSE)) rather than in a public issue, and allow reasonable time for a fix before disclosure.

## Note on repository history

Earlier commits of this repository contained a real-looking `contacts.csv`. It has been removed from the working tree and replaced by fictitious samples. If you fork or mirror the project, be aware that Git history is preserved unless it is rewritten; see [CONTRIBUTING.md](../CONTRIBUTING.md) for the maintainers' guidance on purging sensitive files.
